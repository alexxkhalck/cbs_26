# Заняття 32. Проєктування та нормалізація баз даних

## Мета заняття

Якщо структура бази даних спроєктована невдало, з'являються дублікати даних, помилки оновлення та складнощі з підтримкою системи.

Саме тому перед створенням таблиць виконується проєктування бази даних та її нормалізація.

На цьому занятті ми розглянемо:

* основи проєктування баз даних;
* поняття нормалізації;
* першу, другу та третю нормальні форми;
* аномалії вставки, оновлення та видалення;
* усунення повторюваних груп даних;
* проєктування структури БД для навчального проєкту.

# Що таке проєктування бази даних

Проєктування бази даних — це процес створення структури таблиць, зв'язків та обмежень до початку розробки системи.

Основна мета:

* уникнути дублювання даних;
* забезпечити цілісність інформації;
* спростити підтримку системи;
* покращити продуктивність запитів.

# Приклад поганої структури

Уявімо таблицю замовлень:

| order_id | user_name | phone  | product_1  | product_2 |
| -------- | --------- | ------ | ---------- | --------- |
| 1        | Олександр | 111111 | Ноутбук    | Мишка     |
| 2        | Олександр | 111111 | Клавіатура | NULL      |

На перший погляд усе працює.

Але виникають проблеми:

* ім'я користувача дублюється;
* номер телефону дублюється;
* кількість товарів обмежена колонками;
* складно додати третій товар.

# Навіщо потрібна нормалізація

Нормалізація — це процес усунення надлишковості даних.

Її цілі:

* зменшення дублювання;
* уникнення суперечностей;
* підвищення цілісності даних;
* спрощення змін структури.

Нормалізація виконується за допомогою набору правил, які називаються нормальними формами.

# Що таке нормальна форма

Нормальна форма (Normal Form) — це набір вимог до структури таблиці.

Існує багато нормальних форм:

* 1NF
* 2NF
* 3NF
* BCNF
* 4NF
* 5NF

У більшості бізнес-систем достатньо дотримуватись перших трьох.

# Перша нормальна форма (1NF)

Таблиця перебуває у першій нормальній формі, якщо:

* кожна комірка містить лише одне значення;
* немає списків або масивів у колонках;
* всі записи мають однакову структуру.

# Порушення 1NF

Поганий приклад:

| id | name      | phones  |
| -- | --------- | ------- |
| 1  | Олександр | 111,222 |

У полі `phones` зберігається список значень.

SQL не може ефективно працювати з такими даними.

# Виправлення 1NF

Створюємо окрему таблицю.

### users

| id | name      |
| -- | --------- |
| 1  | Олександр |

### phones

| id | user_id | phone |
| -- | ------- | ----- |
| 1  | 1       | 111   |
| 2  | 1       | 222   |

Тепер кожне поле містить лише одне значення.

# Повторювані групи даних

Ще один приклад порушення 1NF:

| id | product1 | product2 | product3   |
| -- | -------- | -------- | ---------- |
| 1  | Ноутбук  | Мишка    | Клавіатура |

Проблеми:

* кількість товарів обмежена;
* структура негнучка;
* з'являються порожні поля.

# Правильне рішення

### orders

| id |
| -- |
| 1  |

### order_items

| id | order_id | product    |
| -- | -------- | ---------- |
| 1  | 1        | Ноутбук    |
| 2  | 1        | Мишка      |
| 3  | 1        | Клавіатура |

Таку структуру легко масштабувати.

# Друга нормальна форма (2NF)

Для переходу до 2NF таблиця повинна:

1. Відповідати 1NF.
2. Усі неключові поля повинні залежати від повного первинного ключа.

# Приклад порушення 2NF

| order_id | product_id | product_name |
| -------- | ---------- | ------------ |
| 1        | 10         | Ноутбук      |
| 1        | 11         | Мишка        |

Первинний ключ:

```text
(order_id, product_id)
```

Але:

```text
product_name
```

залежить лише від:

```text
product_id
```

а не від повного ключа.

# Усунення порушення 2NF

Розділимо таблицю.

### products

| id | name    |
| -- | ------- |
| 10 | Ноутбук |

### order_items

| order_id | product_id |
| -------- | ---------- |
| 1        | 10         |

Тепер залежності коректні.

# Третя нормальна форма (3NF)

Для переходу до 3NF таблиця повинна:

* відповідати 2NF;
* не містити транзитивних залежностей.

# Що таке транзитивна залежність

Приклад:

| user_id | city | postal_code |
| ------- | ---- | ----------- |
| 1       | Kyiv | 01001       |

Поле:

```text
postal_code
```

визначається через:

```text
city
```

а не через користувача.

Отже виникає транзитивна залежність.

# Усунення порушення 3NF

Створимо окрему таблицю.

### cities

| id | city | postal_code |
| -- | ---- | ----------- |
| 1  | Kyiv | 01001       |

### users

| id | city_id |
| -- | ------- |
| 1  | 1       |

Дані більше не дублюються.

# Аномалія вставки

Аномалія вставки виникає, коли неможливо додати дані без створення інших даних.

Наприклад:

Єдина таблиця:

| user_name | order_amount |
| --------- | ------------ |

Щоб додати нового користувача, потрібно створити замовлення.

Це неправильна структура.

# Аномалія оновлення

Приклад:

| user_name | phone |
| --------- | ----- |
| Олександр | 111   |
| Олександр | 111   |
| Олександр | 111   |

Користувач змінив номер.

Потрібно оновити всі записи.

Якщо забути хоча б один рядок — дані стануть суперечливими.

# Аномалія видалення

Приклад:

| user_name | order |
| --------- | ----- |
| Ірина     | 1000  |

Якщо видалити єдине замовлення Ірини, інформація про користувача також буде втрачена.

# Як нормалізація вирішує ці проблеми

Нормалізація:

* усуває дублікати;
* спрощує оновлення;
* зменшує ризик помилок;
* забезпечує цілісність даних;
* спрощує підтримку системи.

# Етапи проєктування БД

Зазвичай процес виглядає так:

1. Аналіз предметної області.
2. Визначення сутностей.
3. Визначення зв'язків.
4. Створення ER-моделі.
5. Нормалізація.
6. Створення таблиць.

# Що таке сутність

Сутність (Entity) — це об'єкт предметної області.

Приклади:

* користувач;
* замовлення;
* товар;
* курс;
* студент;
* викладач.

Кожна сутність зазвичай стає окремою таблицею.

# Визначення зв'язків

Між сутностями існують зв'язки.

Найпоширеніші:

### Один до одного (1:1)

```text
User → Passport
```

### Один до багатьох (1:N)

```text
User → Orders
```

### Багато до багатьох (M:N)

```text
Students ↔ Courses
```

# Приклад навчального проєкту

Припустимо, ми створюємо систему управління курсами.

Основні сутності:

* students
* courses
* teachers
* enrollments

# Таблиця students

```sql
students
---------
id
first_name
last_name
email
```

# Таблиця teachers

```sql
teachers
---------
id
first_name
last_name
email
```

# Таблиця courses

```sql
courses
---------
id
title
teacher_id
```

Один викладач може вести багато курсів.

# Таблиця enrollments

```sql
enrollments
---------
id
student_id
course_id
created_at
```

Саме ця таблиця реалізує зв'язок:

```text
Студент ↔ Курс
```

# Зв'язки проєкту

```text
teachers
    |
    | 1:N
    |
courses
    |
    | M:N
    |
students
```

Для реалізації M:N використовується таблиця `enrollments`.

# Як зрозуміти, що структура хороша

Хороша структура БД:

* не містить дублювання;
* відповідає 1NF–3NF;
* легко розширюється;
* не створює аномалій;
* підтримує необхідні бізнес-процеси.

# Коли нормалізація може бути надмірною

У великих системах іноді застосовують денормалізацію.

Наприклад:

* дублюють деякі дані;
* створюють агреговані таблиці;
* оптимізують складні звіти.

Але це робиться свідомо після завершення нормалізації.
